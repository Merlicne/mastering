CPU Virtualization

The Fundamentals page showed trap-and-emulate as the general idea. This page covers why plain x86 couldn't actually do it, how Intel and AMD fixed that in hardware, and how KVM and QEMU split the resulting work between kernel and userspace.

Why x86 wasn't classically virtualizable

The Popek-Goldberg theorem gives a precise condition for when trap-and-emulate works cleanly: every instruction that touches privileged state must also be one that traps when a lower-privilege caller runs it. Classic x86 failed this. Researchers identified roughly 17 instructions that were sensitive — they read or changed privileged CPU state — but not privileged: run from ring 3, they didn't trap, they just silently did the wrong thing or returned stale data.

POPF is the textbook example: it's supposed to restore CPU flags, including the interrupt-enable flag — a privileged bit. Run from an unprivileged ring, it doesn't trap and doesn't fail loudly. It just quietly fails to change that one bit, and execution continues as if nothing happened. A hypervisor trying to intercept every privileged operation has nothing to catch here — there's no trap to hook.

The instructions that actually broke it

"Sensitive but not privileged" isn't abstract — it's a specific, short list of x86 instructions. Every one below runs from any ring with no fault at all, which is exactly the problem: there's no trap for a software-only hypervisor to hook.

Instruction(s)What it doesWhy it broke trap-and-emulate
SGDT Stores the Global Descriptor Table register into memory. Hands back the real host GDT base address to any ring — the guest can read genuine machine state the hypervisor never agreed to expose, with nothing to intercept.
SIDT Stores the Interrupt Descriptor Table register into memory. Same problem as SGDT, for the IDT. This is the instruction most often used to literally detect that you're running inside a VM: its returned address falls in a suspiciously different range than bare metal.
SLDT Stores the Local Descriptor Table register. Reveals real LDT state to an unprivileged caller, same shape as SGDT/SIDT.
SMSW Stores the low bits of CR0 (machine status word). CR0 holds privileged control bits; reading it is supposed to be gated, but SMSW isn't — it just returns the truth, unfiltered.
PUSHF / POPF Push/pop the EFLAGS register, including the interrupt-enable (IF) flag. The textbook case: POPF from a demoted guest silently fails to change IF rather than faulting — the guest's attempt to (say) disable interrupts just quietly doesn't happen, with no signal that anything went wrong.
STR Stores the Task Register selector. Same "reveals real state, no fault" shape again, this time for the task register.
LAR / LSL / VERR / VERW Read a segment descriptor's access rights / limit, or verify it's readable/writable at the current privilege level. These evaluate privilege-dependent segment properties directly, without a CPL check gating the instruction itself — so they can return answers based on the guest's real (demoted) privilege level instead of the virtual ring 0 it's supposed to believe it has.

Researchers (Robin & Irvine, 2000) counted roughly 17 such instructions in total on x86 — this table covers the most commonly cited ones, not an exhaustive list. Binary translation patched around every one of them by rewriting guest code; VT-x/AMD-V closed the gap in hardware by adding them to the VMCS/VMCB's configurable exit-cause bitmap, covered next.

Two fixes: binary translation vs. hardware-assisted virtualization

The VMEXIT / VMENTRY cycle

With hardware-assisted virtualization, the CPU gains a new mode dimension on top of the existing rings: VMX root mode (Intel) or the AMD-V equivalent, and VMX non-root mode, where the guest actually runs in real ring 0. A per-vCPU structure — the VMCS (Intel) / VMCB (AMD) — tells the CPU exactly which events should force a VMEXIT — control leaving the guest and landing back with the hypervisor — and later a VMENTRY to resume it. KVM vs. QEMU: who does what

KVM is a Linux kernel module (exposed as /dev/kvm) that owns the VMCS/VMCB and drives the VMENTRY/VMEXIT cycle above. QEMU is an ordinary userspace process that opens /dev/kvm, creates one thread per vCPU, and asks KVM to run the guest. Whenever a VMEXIT happens, KVM either handles it itself (fast — stays in the kernel) or, for anything it doesn't understand (nearly all device I/O), returns control to QEMU, which emulates the device and hands control back.

VMEXIT reasonHandled byWhy
EPT violation → known RAM pageKVM (in-kernel)Just needs a page-table fixup — no need to leave the kernel.
Local APIC / timer accessKVM (in-kernel)Performance-critical and self-contained; KVM emulates the local APIC itself.
I/O port access to a virtio or emulated NIC/diskQEMU (userspace)Device emulation logic lives in QEMU, not the kernel — see the Device & I/O page.
MMIO access to an emulated PCI deviceQEMU (userspace)Same reason — QEMU owns the device models.
CPUIDKVM (in-kernel)KVM reports a filtered/masked feature set so the guest doesn't see host-only CPU features.

This split is exactly why the QEMU & libvirt in Practice page's -enable-kvm flag matters so much: without it, QEMU falls back to TCG, its own software binary translator, and every one of these becomes orders of magnitude slower.

Common gotchas

  • Forgetting -enable-kvm doesn't fail loudly. QEMU silently falls back to TCG software emulation — the VM still boots, just 10-50x slower, which makes it a confusing performance bug rather than an obvious error.
  • Nested virtualization needs the extension exposed through, layer by layer. Running KVM inside a VM requires the outer hypervisor to expose VT-x/AMD-V to that guest — most cloud providers disable this by default, and it must be requested explicitly (e.g. a nested-virtualization-capable instance type).
  • CPU model mismatches break live migration. If the destination host's CPU is missing a feature the guest was told it has (via QEMU's -cpu flag), the guest can crash on migration. Production setups usually pin a conservative, portable CPU model rather than passing through the host's exact features.
  • "Hardware-assisted" doesn't mean "free." Every VMEXIT still costs real cycles — thousands of them — to save/restore state. Reducing VMEXIT frequency (e.g. via virtio's batched, interrupt-coalescing design) is a major reason paravirtualized devices outperform emulated ones.
