Storage: Disk Images & Snapshots

A VM's disk is, from the host's point of view, just a file (or a block device). How that file is structured determines whether snapshots are cheap or impossible, how much space an "empty" 40GB disk actually consumes, and how fast disk I/O really is.

raw vs. qcow2

Copy-on-write and backing files: how a read actually resolves

A qcow2 snapshot doesn't copy the whole disk — it creates a new, initially-empty image that points at the previous one as its backing file. A write always lands in the newest image only; a read for a block the newest image hasn't touched falls through to its backing file, and keeps falling through the chain until it finds a layer that has that block. Common gotchas

  • A snapshot is not a backup. It's stored as a delta on the same physical storage as the disk it's based on — if that underlying storage fails, the snapshot and its base both go with it. Backups need to leave the host entirely.
  • Backing-file chains are fragile. Moving, renaming, or deleting a base image breaks every snapshot built on top of it — qcow2 files reference their backing file by path (or a stored identifier), not by an independent, portable link.
  • Thin provisioning can run out of space unexpectedly. A qcow2 file allocated for a 100GB virtual disk starts small and grows as blocks are written — if several thin-provisioned VMs are overcommitted the same way memory can be, the host can run out of real disk space even though every individual VM reports plenty free.
  • qcow2's extra bookkeeping (copy-on-write, snapshots, compression) costs raw performance. For workloads where you'll never use snapshots and want the smallest possible I/O overhead, a raw image or a raw block device is measurably faster — the tradeoff is losing qcow2's flexibility entirely.
