Memory Virtualization

Memory has the same problem CPU virtualization solved: a guest needs to believe it owns a flat, private address space, while actually sharing physical RAM with the host and every other guest. This page covers how that extra layer of translation works, and the tricks hypervisors use to overcommit memory safely.

The double translation problem

On bare metal, the CPU's MMU does one translation: guest virtual address → physical address, using page tables the OS controls directly. Under virtualization, the guest OS still maintains page tables — but they only translate to guest physical addresses, which aren't real physical memory at all. A second translation, guest physical → host physical, is needed to find where that memory actually lives, and the guest has no idea this second step exists.

Reclaiming memory without violating isolation: ballooning and KSM

TechniqueHow it works
Ballooning A special balloon driver runs inside the guest. To reclaim host memory, the hypervisor asks the balloon to "inflate" — the driver allocates pages inside the guest (making the guest OS think it's under memory pressure and free up or swap out its own least-needed pages), then hands those physical pages back to the host. "Deflating" the balloon later returns memory to the guest. It works entirely through the guest's own memory management, which is why it needs a cooperating, balloon-driver-aware guest.
KSM (Kernel Samepage Merging) The host kernel periodically scans memory pages across all VMs, and where it finds byte-identical pages — extremely common across VMs running the same OS, since large stretches of kernel code, zeroed pages, and common libraries are literally the same bytes — it merges them into a single copy-on-write page. Any VM that later writes to it gets its own private copy transparently. Free, but not without cost: see gotchas below.

Common gotchas

  • The double-paging problem. If the host swaps out a guest's page under memory pressure, and the guest OS independently decides to swap that same page out too, you get redundant, wasteful I/O — the host paging a page the guest itself was about to discard. This is a real argument for preferring ballooning (which works with the guest's cooperation) over blind host-level swapping.
  • Ballooning can trigger guest OOM if inflated too aggressively. The guest genuinely believes memory has become scarce; if the balloon claims more than the guest can comfortably free, the guest's own out-of-memory killer can start terminating processes exactly as it would on real hardware.
  • KSM has a known side-channel risk. Because merging creates real timing differences (writing to a merged page is measurably slower than to a private one, since it triggers copy-on-write), it's been used as a cross-VM information side channel in research attacks. Sensitive multi-tenant environments sometimes disable KSM specifically to close this off.
  • EPT/NPT isn't free just because it's hardware. A TLB miss on virtualized memory needs a full 2-D page walk (guest page table levels × host page table levels — up to 24 memory accesses on x86-64 in the worst case). This is exactly why hypervisors push hard for guests to use huge pages: fewer, bigger pages mean far fewer TLB misses to begin with.
