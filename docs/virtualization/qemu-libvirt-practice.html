QEMU & libvirt in Practice

Everything on the previous four pages shows up as a flag or a command here. This page walks through actually creating a disk, booting a VM with qemu-system-x86_64, giving it real network presence, and snapshotting it — then shows libvirt/virsh as the layer almost everyone actually uses to manage QEMU VMs declaratively instead of by hand, and finally Terraform as one more layer on top of that for managing a whole fleet of them as code.

Building and booting a VM, step by step

Step through the commands in order — each one is explained as you go:

Flag reference

FlagWhat it does
-enable-kvmUse the KVM kernel module for hardware-accelerated CPU virtualization instead of software TCG emulation. See the CPU Virtualization page — omitting this silently falls back to TCG, 10-50x slower, with no error.
-m 4096Guest RAM in MiB. This is the "assigned" number from the Memory Virtualization overcommit calculator.
-smp 4Number of virtual CPUs presented to the guest.
-cpu hostExpose the host CPU's exact feature set to the guest, for maximum performance — at the cost of migration portability, per the CPU page's gotchas.
-drive file=disk.qcow2,if=virtioAttach the qcow2 image via the virtio-blk paravirtualized controller, from the Storage page.
-netdev / -device virtio-net-pciAttach a paravirtualized NIC, from the Device & I/O page. -netdev user is NAT-only (no inbound); -netdev tap bridges the VM onto the real network.
-boot dBoot from the CD-ROM device first — used only for the initial OS install.
-nographic / -vnc :0How you actually see/reach the guest console: serial-over-terminal, or a VNC server QEMU exposes for a remote graphical console.

libvirt: the same VM, managed declaratively

Hand-typing qemu-system-x86_64 flags every time doesn't scale past one or two VMs you manage yourself. libvirt is a management layer: a daemon (libvirtd) that takes a declarative XML "domain" definition and translates it into the equivalent QEMU invocation, tracks the running process, and exposes virsh as a CLI (and an API other tools like virt-manager and OpenStack build on). It's the same underlying QEMU/KVM doing the work — libvirt just stops you from having to remember every flag by hand.

<domain type='kvm'>
  <name>myvm</name>
  <memory unit='MiB'>4096</memory>
  <vcpu>4</vcpu>
  <os><type arch='x86_64'>hvm</type></os>
  <devices>
    <disk type='file' device='disk'>
      <driver name='qemu' type='qcow2'/>
      <source file='/var/lib/libvirt/images/disk.qcow2'/>
      <target dev='vda' bus='virtio'/>
    </disk>
    <interface type='bridge'>
      <source bridge='br0'/>
      <model type='virtio'/>
    </interface>
  </devices>
</domain>
virsh commandWhat it does
virsh define vm.xmlRegister the domain definition above — doesn't start it yet.
virsh start myvmBoot it — libvirtd launches the actual qemu-system-x86_64 process on your behalf.
virsh list --allShow every defined domain and its state (running, shut off, paused).
virsh console myvmAttach to the guest's serial console from the terminal.
virsh snapshot-create-as myvm snap1The libvirt equivalent of the qcow2 external-snapshot step above — managed declaratively instead of raw qemu-img calls.
virsh shutdown / destroy myvmGraceful ACPI shutdown vs. immediate hard power-off (the VM equivalent of pulling the power cable).

Terraform: the same VM, as code

Terraform doesn't talk to QEMU directly — there's no such thing as a "QEMU provider." It goes through libvirt, exactly like virsh does: the community-maintained libvirt provider connects to libvirtd over the same URI (qemu:///system locally, qemu+ssh://user@host/system for a remote hypervisor) and generates the same domain XML you saw above — it's a declarative client of libvirt, not a replacement for it.

terraform.tf — provider setup:

terraform {
  required_providers {
    libvirt = {
      source  = "dmacvicar/libvirt"
      version = "~> 0.7"
    }
  }
}

provider "libvirt" {
  uri = "qemu:///system"
}

main.tf — a base cloud image, a copy-on-write disk derived from it, cloud-init for first-boot config, and the domain itself:

resource "libvirt_volume" "base" {
  name   = "debian-12-generic.qcow2"
  pool   = "default"
  source = "https://cloud.debian.org/images/cloud/bookworm/latest/debian-12-generic-amd64.qcow2"
  format = "qcow2"
}

resource "libvirt_volume" "vm1_disk" {
  name           = "vm1.qcow2"
  pool           = "default"
  base_volume_id = libvirt_volume.base.id   # same backing-file relationship as `qemu-img create -b`
  size           = 21474836480              # bytes -- this is 20GiB, the provider does NOT take GB directly
}

resource "libvirt_cloudinit_disk" "vm1_init" {
  name      = "vm1-cloudinit.iso"
  user_data = <<-EOT
    #cloud-config
    hostname: vm1
    users:
      - name: ops
        sudo: ALL=(ALL) NOPASSWD:ALL
        ssh_authorized_keys:
          - ${file("~/.ssh/id_ed25519.pub")}
  EOT
}

resource "libvirt_domain" "vm1" {
  name      = "vm1"
  memory    = 4096
  vcpu      = 4
  cloudinit = libvirt_cloudinit_disk.vm1_init.id

  disk {
    volume_id = libvirt_volume.vm1_disk.id
  }

  network_interface {
    bridge = "br0"   # same TAP/bridge setup as the Device & I/O page
  }
}

output "vm1_ip" {
  value = libvirt_domain.vm1.network_interface[0].addresses[0]
}
CommandWhat it does
terraform initDownloads the libvirt provider plugin and initializes the working directory. Run once per project (and after adding new providers).
terraform planShows exactly what would be created/changed/destroyed by diffing this config against Terraform's state file — nothing touches libvirtd yet.
terraform applyActually creates the volumes and domain, in dependency order (base image, then the derived disk, then the domain) — under the hood this is the same libvirt API calls virsh define and virsh start make.
terraform destroyTears down everything this config created — the domain, its disks, the cloud-init ISO. Only removes what's tracked in state.
terraform import libvirt_domain.vm1 vm1Adopts a VM you already created by hand (via virsh or raw qemu-system-x86_64) into Terraform's state, so future changes go through Terraform instead of conflicting with it.

Common gotchas

  • /dev/kvm permission errors are the most common first-run failure. Access is normally restricted to a kvm group; your user needs to be a member (and re-login for the group change to apply) before -enable-kvm will work at all.
  • -netdev user is NAT-only and easy to mistake for real networking. It's the simplest way to get a VM online, but the VM isn't reachable from the rest of your network without explicit hostfwd port forwards — for a VM other machines need to reach directly, TAP + bridge (from the Device & I/O page) is what's actually needed.
  • Mixing hand-run QEMU and libvirt-managed VMs causes confusion. A VM started directly with qemu-system-x86_64 is invisible to virsh list — libvirt only knows about domains it started itself. Pick one management approach per VM.
  • An external snapshot's overlay file is exactly the fragile backing-chain setup from the Storage page. Don't move or delete disk.qcow2 while overlay.qcow2 is in use — the overlay only stores the delta and depends on the base being right where it left it.
  • Hand-editing a Terraform-managed VM is the same split-brain problem, one layer up. Running virsh edit or virsh destroy on a domain Terraform created causes state drift — Terraform's state file still thinks the old config is what's running, and the next terraform apply either fights the manual change or tries to recreate the resource from scratch. Adopt existing domains with terraform import instead of mixing management approaches.
  • The libvirt provider's size is in bytes, not GB. A config meant to create a 20GiB disk that instead sets size = 20 silently creates a 20-byte volume — the provider won't warn you, and the resulting VM will fail to boot with a confusing "no bootable device" error that has nothing obviously to do with the real cause.
