Device & I/O Virtualization

CPU and memory virtualization (previous two pages) let a guest run its own code safely. Devices are a separate problem: a guest still needs to talk to disks and network cards it doesn't actually own. There are three fundamentally different ways to give it that access, trading off performance, guest compatibility, and flexibility very differently.

Two optimizations worth knowing by name: vhost-net moves the QEMU-side packet-copying step into the kernel, skipping a userspace round trip; macvtap replaces the bridge with a more direct interface-to-interface mapping when you don't need full bridge features. Both keep the same virtio-net guest driver — only the host-side path changes.

Common gotchas

  • virtio needs a cooperating guest. It's paravirtualization (see Fundamentals) — an ancient or unusual guest OS without virtio drivers has to fall back to slower fully-emulated devices (e.g. an emulated e1000 NIC or IDE controller) instead.
  • PCI passthrough requires IOMMU support, enabled at multiple layers. The CPU, the motherboard/BIOS, and the host kernel all need IOMMU (VT-d on Intel, AMD-Vi on AMD) turned on — it isolates the passed-through device's DMA so it can only touch that guest's memory, not the whole host's.
  • Passthrough breaks live migration. A physical device passed straight through is physically attached to one specific host — there's no way to move a running VM using it to different hardware without first detaching the device. This is the single biggest reason virtio remains the default even when passthrough would be faster.
  • SR-IOV isn't "passthrough but shared" for free. It requires a physical NIC that itself supports SR-IOV and exposes multiple Virtual Functions (VFs) in hardware; the number of VFs is fixed by the NIC, not something software can expand.
