Fundamentals & Hypervisor Types

A hypervisor lets one physical machine run several guest operating systems, each believing it owns the whole computer. Nothing about that is obvious — a guest kernel is written assuming it's in full control of the hardware. This page covers why the trick works at all, the two ways hypervisors are built, and how this differs from the container isolation you may already know from Kubernetes.

Why virtualization is possible: privilege rings and trap-and-emulate

x86 CPUs expose four privilege rings. In a normal, non-virtualized machine, the kernel runs in ring 0 — it can do anything, including instructions that reconfigure the CPU itself — while ordinary applications run in ring 3, restricted to a safe subset. A guest kernel under a hypervisor still thinks it's running in ring 0. It isn't: the hypervisor demotes it, and reserves the truly privileged level for itself.

Ring -1Hypervisor (VMX root mode) — the only fully privileged code on the machine
Ring 0Guest kernel — believes it's fully privileged, actually isn't
Rings 1 & 2 — defined by x86, essentially unused by modern OSes
Ring 3Guest applications — same restricted level as on bare metal

When the demoted guest kernel tries to execute an instruction only ring -1 is actually allowed to run, the CPU traps instead of executing it. The hypervisor inspects the trap, emulates the effect the guest expected, updates the guest's virtual state accordingly, and resumes the guest — which never notices anything happened. Type 1 vs. Type 2 hypervisors

The two categories differ in what sits directly on the hardware:

Three ways to virtualize, compared

ApproachWhat's virtualizedGuest OS aware it's virtualized?Example
Full virtualization Complete hardware — CPU, memory, devices No — runs an unmodified guest kernel QEMU/KVM, VMware, Hyper-V
Paravirtualization Same, but the guest kernel is modified to call the hypervisor directly instead of triggering traps Yes — guest kernel is virtualization-aware Xen PV, virtio drivers
OS-level virtualization (containers) Nothing at the hardware level — processes are isolated by the host kernel itself N/A — there is no separate guest kernel Docker, containerd

Most real deployments blend the first two: a fully virtualized CPU and memory, but paravirtualized (virtio) devices for speed — exactly the QEMU/KVM default covered on the Device & I/O and QEMU & libvirt in Practice pages.

Containers vs. VMs: a different isolation boundary entirely

It's tempting to think of a container as "a lightweight VM," but the isolation boundary sits in a completely different place. A VM's guest gets its own kernel, virtualized down to the CPU and memory level; a container is just a regular host process, isolated using the host kernel's own namespaces and cgroups. There's no hypervisor, no guest kernel, no ring demotion at all.

That shared kernel is the whole tradeoff: containers start in milliseconds and pack far denser because there's no second OS to boot, but a kernel-level vulnerability is a much bigger deal — it potentially affects every container on the host, not just one guest. A VM's isolation boundary is enforced by the CPU itself (see the trap-and-emulate demo above); a container's is enforced entirely in software, by the host kernel's own bookkeeping. Common gotchas

  • "Lightweight VM" is a misleading way to describe a container. The performance difference isn't a matter of degree — containers skip the entire guest-kernel-plus-hypervisor layer rather than having a smaller one.
  • Nested virtualization is a real thing, not a contradiction. A hypervisor can itself run inside a VM (e.g. running KVM inside a cloud VM), but it needs the host to expose virtualization extensions through to the guest — it's off by default on most cloud providers and must be explicitly enabled.
  • KVM blurs the Type 1/Type 2 line on purpose. It turns the Linux kernel itself into a Type 1 hypervisor (no separate hypervisor OS to install), while device emulation still happens in an ordinary userspace process — QEMU. See the CPU Virtualization page for exactly how that split works.
  • Paravirtualization needs a cooperating guest. It only works if the guest kernel ships the right drivers/awareness (e.g. virtio) — you can't paravirtualize an OS that has no idea it's supposed to cooperate.
