Node Components & Container Runtime

The Architecture page covered the control plane's decisions. This page covers what actually turns those decisions into running containers on a worker node.

kubelet: the node's agent

kubelet watches the API server for Pods assigned to its own node, and makes sure the containers described in each PodSpec are actually running — starting them if they're missing, restarting them if they crash, and reporting status back. It also runs three kinds of health checks:

ProbeOn failure
Liveness probekubelet restarts the container
Readiness probeRemoved from Service endpoints (see Kubernetes Networking) — container keeps running
Startup probeBlocks the other two probes until it passes, protecting slow-starting apps

The container runtime & CRI

kubelet doesn't create containers itself — it delegates to a container runtime through the CRI. This is the same namespace/cgroup machinery from Linux Networking and Container Networking — Kubernetes doesn't invent a new isolation mechanism, it orchestrates the one Linux already provides.

Historical note: Kubernetes removed "dockershim" (its compatibility layer for Docker, which didn't speak CRI natively) in v1.24. Docker itself is built on containerd, so most workloads were unaffected — what disappeared was a compatibility shim, not the underlying engine.

The pause container: how a Pod shares one network namespace

When a Pod is created, the runtime first creates an infrastructure container — often literally called "pause" — whose only job is to hold open the Pod's shared namespaces (network, and optionally others). Every other container in that Pod joins this same namespace instead of getting its own. That's the entire mechanism behind something you may have taken for granted: containers in the same Pod can reach each other over localhost, exactly like processes on the same machine.

Common gotchas

  • The pause container barely does anything — that's the point. Its entire job is to hold namespaces open so other containers can join them, even in the brief moment it's the only container running.
  • Liveness and readiness failures have very different consequences. Confusing the two is a common way to accidentally restart a perfectly healthy container that's just temporarily busy — that container needed a readiness probe, not a liveness one.
  • Removing dockershim didn't remove Docker's engine. It removed Kubernetes' compatibility layer for talking to Docker's non-CRI-native API — Docker itself runs on containerd underneath.
  • kubelet only manages its own node. It never talks to other nodes' kubelets, and it makes no scheduling decisions — placement is entirely the scheduler's job, from the Architecture page.
