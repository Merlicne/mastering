Policy & Security

"Policy" in Kubernetes spans several independent layers: who can do what (RBAC), how privileged a Pod is allowed to be, how much a namespace can consume in aggregate, and a final checkpoint before anything is persisted. This page covers all of them except NetworkPolicy, which already has its own page in the Networking subject.

RBAC: purely additive, no explicit deny

RBAC works by accumulating grants: a Role or ClusterRole lists what's allowed, and a RoleBinding or ClusterRoleBinding hands it to someone. There is no explicit deny rule anywhere in the model — this is exactly the same "allow-only" shape as cloud security groups from the Firewalls page.

Pod Security Admission: how privileged can a Pod be?

Pod Security Admission enforces one of three standards, applied by labeling a namespace — not individual Pods:

StandardWhat it allows
PrivilegedNo restrictions — full access to the host, if the Pod asks for it
BaselineBlocks known privilege escalations, but stays broadly compatible with common workloads
RestrictedHeavily hardened — must run as non-root, no privilege escalation, seccomp required

Admission controllers & webhooks: the last checkpoint before etcd

This is the same stage from Architecture's "life of a kubectl apply" step-through: after authentication and RBAC authorization, every request runs through mutating admission webhooks first, then validating admission webhooks. Order is deliberate: by the time validation runs, the object already reflects every mutation, so validators always see its final shape. General-purpose policy engines like OPA/Gatekeeper and Kyverno plug in at exactly this point.

Common gotchas

  • RBAC has no explicit deny. The only way to restrict something already granted broadly is to not grant it that broadly in the first place — not to add a deny rule on top, because there isn't one.
  • cluster-admin is extremely powerful and often over-granted. Binding it to a service account "just to get something working" is one of the most common real-world RBAC mistakes — there's no way to partially revoke pieces of it later.
  • Pod Security Admission is opt-in per namespace. A brand-new namespace has no enforcement at all until someone remembers to label it — there's no cluster-wide default that silently protects every namespace.
  • A ResourceQuota can suddenly start rejecting Pod creation. Once a namespace's quota covers compute resources, every Pod in it must specify requests/limits or be rejected outright — this surprises teams that never had to specify these before the quota existed.
